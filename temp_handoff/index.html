    Temp 品牌審核交接方案（2026-09-22）

    本方案適用 momo 此次來源的 545,572 品號、22 個 L1。工作目標是確認商品的實際品牌、對應既有 brand_id，並提出有證據的新品牌候選。Temp 不負責建立正式品牌、合併品牌庫 ID、改程式或直接操作資料庫。

    開始前

    由專案負責人提供這次產出的 review/momo/_momo_全站審核總表_Temp用.xlsx，以及 brand_pool.csv 品牌查詢表。舊總表停止使用。所有人只用同一批次，按 key 分配，每個 key 只給一位 Temp；不能單純按 L1 分工，因為品牌會跨類目重複。

    先篩選 ① 待審 與 ② 抽查；③ 已審、④ 自動 不要求 Temp 逐筆重做。新品牌即使信心高也會進總表的待審；不要把信心分數當作準確率或已核准新增。

    分類、動作與 scope

    分類 Temp 明確動作 套用範圍 完成條件／升級
    A 跨類目衝突 查看「各類目建議」，查不同類目的商品頁，備註每個實際品牌與證據 不可整組套用 判斷留白；交主管拆成單品覆蓋或重新設計規則
    B 新品牌查證 先判斷中括號是否為品牌，再搜尋品牌庫的中文、英文、別名 B:/T: key 相同的商品；有異質商品立即升級 已有品牌填 ID；確為新品牌填 新增:正式名稱、附查證來源；主管複核後才送建檔
    C 單品／配件辨識 看品牌欄、商品頁與包裝，區分製造商與相容主機 I:品號 僅該品號 有製造品牌填 ID；無品牌須填原因；不確定則留白並備註
    D 無品牌確認 確認不是漏掉品牌、出版社或獨立配件品牌 以該列套用範圍為準 確認無品牌才填 No brand＋原因；僅看到促銷詞不能證明整件商品無品牌
    E 既有品牌配對 核對品牌實體、中英文、類目；同實體才比較 adg B:/T: key 相同的商品 填 brand_id 或候選 1/2/3；多個不同品牌都合理則留白、交主管

    B: 來自品牌欄，T: 來自有效中括號，兩者規則都跨 L1 共用。I: 是單品隔離 key。不可修改 key、系統候選、建議 ID、規則版本或範例連結來改變 scope；只改人工欄。若同 key 內有多個實際品牌，不能做全組判斷；主管使用各 L1 的「單品覆蓋」頁填實際品號。

    判斷範例

    • 【買一送一】、【超抗刮】、【洗衣機過濾網】、【台灣製造】 不是新增品牌證據。繼續看商品本身是否有品牌。
    • iPhone 是產品線。本次 Apple 同實體最高 adg 是 Apple [1189223]，不是 iphone [5235256]。不要把 Apple House、蘋果西打等其他品牌納入比較。
    • 【犀牛盾】iPhone 保護殼 看犀牛盾；【Apple】iPhone 保護殼 需查是否原廠，不能只靠主機名判定。
    • 出版社／出版品牌不因出現在 Books 就自動判成描述；保留查證程序。
    • 找不到資料不是 No brand，也不是新增品牌。判斷留白，備註 待確認｜原因｜已查來源。

    備註建議格式：結論依據｜商品/品牌官網URL｜確認的正式名稱｜查過的別名｜審核人｜日期。新增品牌及修正 ID 必須有證據；跨類目案件需記錄多個類目的實際商品，不只看總表第一個範例。

    試作與驗收（建議門檻，不是已測得的準確率）

    1. 先分派 100 個 key 做校準，涵蓋 B–E 四類，各至少 20 個；A 類由主管示範。主管全數複核，釐清品牌／產品線／店家／描述的邊界。
    2. 校準達 95% 一致、且沒有把產品線當品牌或誤做全站覆蓋，再按每批 300 個 key 分派。同分類內優先商品數多的列。
    3. 每批新品牌、跨類目衝突、Apple／相容配件高風險案件 100% 複核；其餘隨機抽 10%，每批至少 30 列。抽查未達 95% 或出現 scope 錯誤，退回該類重做。
    4. 回報「已分派／已查證／待主管／未完成」的 key 數及對應商品數。不能把留白算完成；不能用涵蓋商品數宣稱准确率。

    人力及工期先不硬估。記錄試作每類的查證分鐘數，使用 各類剩餘 key × 試作平均分鐘 ÷ 每日有效工作分鐘 排程；新增品牌與單品案件通常需要不同工時。

    回灌與操作責任

    Temp 只填表；專案負責人備份資料庫和審核檔後，執行：

    py run.py bundle-import --file <本批已複核總表.xlsx>
py run.py tag --all
py run.py bundle-export
py run.py export

    每批僅保留一份正式回傳檔，不同人有衝突時先由主管裁決。跨類目衝突列有判斷會被拒絕；驗證錯誤整批不匯入，修好後重試。舊表不能覆蓋較新的品牌規則；不要刪掉規則版本來繞過保護。不要同時開啟多個 tagging／匯入程序。

    新增建議只寫入本專案的候選狀態，不會建立品牌庫 ID。主管核准、品牌庫負責人建檔並更新 pool 後，再以正式 ID 重跑。審核期間不要修改自動學習別名或直接改資料庫。

    檢查邊界與仍須注意的事項

    • 文字規則是啟發式，沒有逐件讀取 54 萬個商品頁，因此不能保證所有非品牌描述已排除。新增建議與不確定配件必須查證。
    • 非配件且同 key 的商品仍以代表商品做自動判斷；總表能阻擋跨類目「結論不同」的衝突，不能證明同組所有商品都是同品牌。Temp 查到反例時必須升級，不能整組套用。
    • 未知／短品牌名、相容品缺少獨立中括號品牌，仍可能被暫判 No brand。No brand 抽查不可省略。
    • 歷史別名含 auto / curated / human；撤銷品牌規則不等於刪除所有歷史別名。涉及別名誤學由專案負責人處理，不給 Temp 做批次撤銷。
    • 本次來源快取與結果有核對品號覆蓋；不代表重新核對 raw 中每筆 SKU payload 的完整語義。

    可重現檢核程式：analysis/project_audit.py；執行前後證據與備份在 output/audit_20260922/。
